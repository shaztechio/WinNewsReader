# Security Review Report

A defensive security audit of the WinNewsReader repository was conducted across all C# projects (`src/App`, `src/Cli`, `src/Core`, `src/Parser`, `src/Store`, `src/Sync.Feedbin`, `src/Sync.GoogleReader`, `src/Sync.NewsBlur`), test suites (`tests/*`), Windows packaging scripts (`packaging/windows/*`), tooling (`tools/*`), static website files (`site/*`), and GitHub Actions workflows (`.github/workflows/*`). The codebase demonstrates strong defensive practices overall, including parameterized SQLite queries throughout `ArticlesStore`, Windows Credential Manager integration for account secrets, strict zip-slip and zip-bomb protections in `ArticleThemeInstaller`, DTD/entity expansion prohibition when parsing `Info.plist`, and scheme checks on external browser navigation. Five security findings were identified: three in application code (which were fixed in this review) and two in GitHub Actions workflow files (reported as not fixed per review constraints on `.github/workflows/`).

## Detailed Findings

### SEC-01: Unescaped HTML and Attribute Injection in Rendered Article Header Metadata and Byline

- **Severity:** Medium (CWE-79)
- **Location:** `src/Core/ArticleRendering/ArticleRenderer.cs:224-308`
- **Status:** Fixed
- **Description:**
  `ArticleRenderer.Substitutions` and `ArticleRenderer.Byline` populated macro variables for `template.html` (`preferred_link`, `external_link`, `external_link_stripped`, `avatar_src`, `feed_link_title`, `feed_link`, and author `Name`, `Url`, and `EmailAddress` in `byline`) without escaping XML/HTML special characters (`&`, `<`, `>`, `"`, `'`). While `ArticleRenderer.EnclosureHtml` and `ArticleText.PlainTextToHtml` escaped special characters, the header substitutions inserted feed-supplied metadata directly into `<a href="...">...</a>` and `<img src="...">` elements.
- **Impact:**
  A malicious or malformed feed containing HTML markup or double quotes in the feed title, author name/email/URL, or article link URLs could break out of HTML attributes and inject arbitrary HTML or scripts into the article header in WebView2, even when the article body itself is plain text (`content_text`).
- **Changes Made:**
  Applied `ArticleText.EscapingSpecialXmlCharacters` to `preferred_link`, `external_link_stripped`, `external_link`, `avatar_src`, `feed_link_title`, `feed_link`, and all author fields (`Name`, `Url`, `EmailAddress`) in `Byline` in `src/Core/ArticleRendering/ArticleRenderer.cs`, and added unit test coverage in `tests/Store.Tests/ArticleRenderingTests.cs`.

### SEC-02: Basic Authentication Credential Leakage via Unvalidated `Link` Pagination URL

- **Severity:** Medium (CWE-522)
- **Location:** `src/Sync.Feedbin/FeedbinCaller.cs:166-175`
- **Status:** Fixed
- **Description:**
  During entry synchronization, `FeedbinAccount.ProcessPagesAsync` follows pagination URLs extracted from the HTTP `Link: <...>; rel="next"` response header and passes them to `FeedbinCaller.GetEntryPageAsync`, which calls `FeedbinCaller.SendAsync`. `SendAsync` accepted any `pathOrUrl` starting with `"http"` and unconditionally attached `request.Headers.Authorization = _authorization` (the user's HTTP Basic Authentication header containing base64-encoded `email:password`) without verifying that the URL belonged to the configured `_baseAddress`.
- **Impact:**
  If a response header contained a `rel="next"` pagination link pointing to an external domain or a plaintext `http://` URL, `FeedbinCaller` would transmit the user's Basic Auth credentials to that untrusted host or over cleartext HTTP.
- **Changes Made:**
  Updated `FeedbinCaller.SendAsync` in `src/Sync.Feedbin/FeedbinCaller.cs` to verify that any full URL passed in `pathOrUrl` starts with `_baseAddress` before sending the request with credentials, throwing a `FeedbinException` otherwise, and added unit test coverage in `tests/Sync.Feedbin.Tests/FeedbinAccountTests.cs`.

### SEC-03: Single-Instance Named Pipe Created Without `PipeOptions.CurrentUserOnly`

- **Severity:** Low (CWE-284)
- **Location:** `src/App/SingleInstance.cs:43-60`
- **Status:** Fixed
- **Description:**
  `SingleInstance.ListenAsync` and `SingleInstance.Send` created `NamedPipeServerStream` and `NamedPipeClientStream` without `PipeOptions.CurrentUserOnly`.
- **Impact:**
  On a multi-user Windows machine, another local user account could connect to the running user's `WinNewsReader-<hash>` named pipe to inject launch targets (such as local `.nnwtheme` or `.opml` paths or `feed:` URLs) into the running session, or pre-create the pipe instance between connections.
- **Changes Made:**
  Added `PipeOptions.CurrentUserOnly` to both `NamedPipeClientStream` and `NamedPipeServerStream` in `src/App/SingleInstance.cs`.

### SEC-04: Unvalidated `github.ref_name` Interpolated Directly into PowerShell `run:` Blocks

- **Severity:** Medium (CWE-78)
- **Location:** `.github/workflows/release.yml:34-42`
- **Status:** Not fixed (workflow file)
- **Description:**
  In `.github/workflows/release.yml`, `${{ github.ref_name }}` and `${{ steps.version.outputs.version }}` are interpolated directly into PowerShell `run:` scripts (lines 34, 42, 90, 91, 110, 134, 137) without environment variable indirection or strict format validation on the extracted version string.
- **Impact:**
  If a tag matching `v*` with shell/PowerShell metacharacters or MSBuild property injection characters is pushed, direct `${{ ... }}` interpolation in `run:` blocks can alter command arguments or execute unintended PowerShell expressions during a privileged release workflow with `contents: write` and `pages: write` permissions.
- **Recommended Fix:**
  Pass `github.ref_name` and `steps.version.outputs.version` through step `env:` variables (e.g., `REF_NAME: ${{ github.ref_name }}` and `VERSION: ${{ steps.version.outputs.version }}`), reference `$env:REF_NAME` and `$env:VERSION` in PowerShell, and validate `$version` in the `version` step with:
  ```powershell
  $version = $env:REF_NAME.TrimStart("v")
  if ($version -notmatch '^\d+\.\d+\.\d+(-[0-9A-Za-z.-]+)?$') {
    throw "Invalid release version tag: $env:REF_NAME"
  }
  ```

### SEC-05: Unpinned Global Tool Installation (`dotnet tool install -g vpk`) in Release and Pages Workflows

- **Severity:** Low (CWE-829)
- **Location:** `.github/workflows/release.yml:45` (and `.github/workflows/pages.yml:36`)
- **Status:** Not fixed (workflow file)
- **Description:**
  Both `.github/workflows/release.yml` (line 45) and `.github/workflows/pages.yml` (line 36) run `dotnet tool install -g vpk` without specifying `--version`, always pulling the latest published version of `vpk` from NuGet at workflow runtime, even though `src/App/WinNewsReader.App.csproj` pins `<PackageReference Include="Velopack" Version="0.0.1298" />`.
- **Impact:**
  Installing an unpinned packaging and code-signing orchestration tool in the release pipeline exposes release builds (which have access to code-signing credentials and GitHub Pages deployment permissions) to supply-chain compromise or breaking behavioral changes in newly published `vpk` versions.
- **Recommended Fix:**
  Pin the `vpk` CLI version to match the `Velopack` package reference in `src/App/WinNewsReader.App.csproj`:
  ```yaml
  run: dotnet tool install -g vpk --version 0.0.1298
  ```
